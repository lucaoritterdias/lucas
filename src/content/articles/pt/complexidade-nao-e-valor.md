## Tecnologia deve desaparecer

Para quem usa um produto, a melhor tecnologia costuma ser aquela que não chama atenção para si. A tela responde, a informação chega e o trabalho avança. Por trás dessa simplicidade pode existir muito esforço, mas ele não deve ser transferido para o usuário na forma de mais um passo, mais uma tela de confirmação, mais uma decisão que não é dela.

Quando um sistema exige explicação constante para ser usado, normalmente o problema não é falta de treinamento, é excesso de decisão técnica exposta. A engenharia que se orgulha de si mesma na interface geralmente cobrou um preço em clareza de quem só queria terminar a tarefa.

## Toda escolha cobra manutenção

Cada ferramenta, integração ou camada adicionada ao projeto cria uma responsabilidade futura. A pergunta não é apenas se algo pode ser implementado, mas se merece continuar existindo pelos próximos anos, sendo atualizado, monitorado e explicado para quem chegar depois. Essa mudança de perspectiva evita que entusiasmo técnico vire custo operacional.

É fácil justificar uma nova dependência olhando apenas para o problema de hoje. É mais difícil, e mais valioso, perguntar quem vai atualizar essa peça daqui a dois anos, quando a pessoa que a escolheu já não estiver no time. Repertório é, em boa parte, lembrar dessa pergunta antes de escrever a primeira linha.

## Simplicidade exige repertório

Simplificar não é fazer menos por falta de capacidade. É compreender o problema o suficiente para remover o que não contribui. Depois de muitos projetos, percebi que as melhores decisões raramente são as mais chamativas, são as que deixam o caminho mais claro para quem vem depois, seja um usuário, seja outro desenvolvedor.

Isso costuma exigir mais discussão, não menos: entender o motivo de cada requisito antes de aceitá-lo, questionar se uma exceção é realmente necessária ou apenas conveniente no momento. Simplicidade bem-feita parece óbvia depois de pronta, mas raramente é o primeiro caminho que aparece.

## O custo invisível das exceções

Toda exceção parece pequena quando é criada. "Só esse cliente precisa de um fluxo diferente", "só nesse caso o cálculo muda", "é temporário até resolvermos aquele outro problema". Individualmente, cada uma é razoável. Juntas, formam um sistema onde ninguém consegue prever o comportamento com confiança, porque as regras já não são as mesmas para todo mundo.

Um sinal de maturidade técnica é notar isso cedo: perguntar, antes de aceitar uma exceção, se ela resolve um problema real ou apenas adia uma conversa incômoda sobre o que o produto deveria fazer. Nem toda exceção deve ser recusada, mas toda exceção deveria ser consciente, documentada e, de preferência, com prazo de validade.

## Simplificar é uma decisão de negócio, não só técnica

É tentador tratar simplicidade como preferência de engenharia, um gosto por código limpo. Mas cada camada removida também é dinheiro e tempo preservados para o negócio: menos suporte, menos treinamento, menos gente necessária para operar o mesmo sistema. Complexidade desnecessária não é apenas um problema estético, é um custo recorrente que aparece na fatura de manutenção todo mês.

Por isso, decisões de simplicidade deveriam sentar na mesma mesa que decisões de produto e de negócio. Quando isso acontece, "vamos manter simples" deixa de ser um capricho técnico e passa a ser, com frequência, a decisão financeiramente mais responsável.
